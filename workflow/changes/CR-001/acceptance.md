## 状态规则

- `状态` 记录工程推进状态：`Pending`、`Designed`、`Implemented`、`Verified`、`Blocked`。
- `覆盖状态` 记录覆盖结论，只允许使用：
  - `covered`：已有实现证据和测试证据。
  - `not_covered`：尚未覆盖，必须写明原因。
  - `manual_pending`：只能人工验证，必须在人工验收范围中列出。
  - `deferred_with_approval`：已获 PL/用户批准暂缓，必须写明批准依据。
  - `out_of_scope_with_reason`：确认不属于本 CR，必须写明原因。
- P0/P1 验收项不得缺少 `覆盖状态`、`未覆盖原因` 或 `PL 处理`。

## 维护规则

- PM 负责从 OpenSpec proposal 和 `specs/**/spec.md` 写入验收项。
- PM 必须给每个验收项分配稳定的 `REQ-*` 和 `AC-*` 编号。
- Architect 负责补设计落点。
- Frontend / Backend / Admin / AI 实现 Agent 负责补实现证据、验证记录和执行日志；PL 根据执行证据汇总更新 OpenSpec task 状态。
- QA 负责独立复核测试证据和覆盖状态。
- PL 在需求关口、设计关口和发布关口检查矩阵完整性。
- 需求关口前必须至少有可测试的验收标准和非空覆盖状态。
- 设计关口前必须补齐设计落点、OpenSpec task 和测试用例 / 验证引用，状态不应停留在 `Pending`。
- 发布关口前，P0/P1 只能是 `covered`、`deferred_with_approval` 或 `out_of_scope_with_reason`；不能把 `not_covered` 写成通过。
