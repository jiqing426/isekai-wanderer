# 剧本结构优化方案

## 背景

根据《剧本结构设计规范》文档对比当前系统实现，发现以下主要差异：

| 差异项 | 文档要求 | 当前实现 | 差距 |
|--------|----------|----------|------|
| 章节结构 | 4章节（相遇/日常/冲突/收束） | 无章节概念，用route替代 | 结构缺失 |
| 收敛节点 | 每路线3个（共9个/剧本） | 几乎为0 | 数据缺失 |
| 结局类型 | 4种（Good/Normal/Bad/Secret） | 3种（无Secret） | 类型缺失 |
| 节点类型 | 开场/AI对话/选择/收敛/结局/CG | 部分实现 | 类型不完整 |
| 碎片选项 | 消耗碎片解锁彩蛋 | 字段存在，逻辑不完整 | 功能不完整 |
| 时间约束 | 3分钟内进入第一个选择点 | 无约束 | 规则缺失 |
| 好感度触发CG | 好感度≥20自动触发 | 未绑定 | 规则缺失 |
| 选择项数量 | 统一3个 | 部分2个，部分3个 | 数据不一致 |

## CR-030: 章节结构重构

### 问题描述

当前系统没有"章节"概念，而是用route表示不同剧情分支。文档要求每个剧本有明确的4章结构：
- 第一章：相遇（10-15轮对话）
- 第二章：日常（20-30轮对话）
- 第三章：冲突（15-20轮对话）
- 第四章：收束（10-15轮对话）

### 当前数据

```
星月奇缘：3条路线（第一章/第二章/第三章），共36节点
星辰之约：4条路线，共32节点
樱花恋曲：4条路线，共24节点
```

### 优化方案

**方案A：新增chapter字段（推荐）**

1. **数据库改动**
   ```sql
   -- routes表新增chapter字段
   ALTER TABLE routes ADD COLUMN chapter_number INTEGER;
   ALTER TABLE routes ADD COLUMN chapter_type VARCHAR(50);
   -- chapter_type: encounter/daily/conflict/convergence
   ```

2. **数据迁移**
   - 将现有route按章节规则重新组织
   - 例如：星月奇缘的"第一章：月夜邂逅" → chapter_number=1, chapter_type='encounter'

3. **API改动**
   - `/game/{session_id}/status` 返回当前章节信息
   - `/scripts/{id}/chapters` 返回剧本章节列表

4. **前端改动**
   - 进度条显示"第X章：章节名"
   - 章节切换时显示过渡动画

**方案B：保持现有route结构，增加章节映射**

1. **新增映射表**
   ```sql
   CREATE TABLE route_chapters (
     id UUID PRIMARY KEY,
     route_id UUID REFERENCES routes(id),
     chapter_number INTEGER,
     chapter_type VARCHAR(50),
     start_node_id UUID REFERENCES nodes(id),
     end_node_id UUID REFERENCES nodes(id)
   );
   ```

2. **优点**：不破坏现有结构，兼容性好
3. **缺点**：查询复杂，需要额外JOIN

### 推荐方案

**方案A**：新增chapter字段，理由：
- 结构清晰，符合文档规范
- 查询简单，性能好
- 前端展示直观

### 工作量评估

| 任务 | 工时 |
|------|------|
| 数据库迁移脚本 | 4h |
| 数据迁移（3个剧本） | 8h |
| 后端API改动 | 8h |
| 前端章节展示 | 8h |
| 测试验证 | 4h |
| **合计** | **32h（4天）** |

## CR-031: 收敛节点数据填充

### 问题描述

文档要求每条路线有3个收敛节点（对应第2/3/4章），当前系统中converge_node类型节点几乎为0。

### 当前数据

```
星月奇缘：3条路线，converge_node=0
星辰之约：4条路线，converge_node=1（仅"林辰线"有1个）
樱花恋曲：4条路线，converge_node=0
```

### 优化方案

1. **数据填充规则**
   - 每条路线必须有3个收敛节点
   - 收敛节点位置：第2章末、第3章末、第4章末
   - 收敛节点类型：`node_type='converge_node'`

2. **填充计划**
   ```
   星月奇缘：3路线 × 3收敛节点 = 9个
   星辰之约：4路线 × 3收敛节点 = 12个（已有1个，需补11个）
   樱花恋曲：4路线 × 3收敛节点 = 12个
   合计：需新增32个收敛节点
   ```

3. **收敛节点内容**
   - 固定剧情（人工预设）
   - 多路线汇合点
   - 触发CG或关键剧情

### 工作量评估

| 任务 | 工时 |
|------|------|
| 收敛节点内容设计 | 8h |
| SQL脚本编写 | 4h |
| 数据填充执行 | 2h |
| 测试验证 | 2h |
| **合计** | **16h（2天）** |

## CR-032: Secret End实现

### 问题描述

文档要求4种结局类型（Good/Normal/Bad/Secret），当前系统缺少Secret End。

### 当前数据

```
结局类型分布：
- good: 4个
- normal: 1个
- bad: 1个
- secret: 0个（缺失）
```

### 优化方案

1. **数据库改动**
   ```sql
   -- endings表已有type字段，无需改动
   -- 新增secret_end条件字段
   ALTER TABLE endings ADD COLUMN secret_condition JSONB;
   -- secret_condition示例：
   -- {"required_affection": 80, "required_choices": ["choice_id_1", "choice_id_2"]}
   ```

2. **后端改动**
   - 结局判断逻辑增加Secret End检查
   - 检查条件：跨路线特定选择 + 好感度阈值

3. **前端改动**
   - Secret End特殊展示效果
   - 解锁提示（"发现隐藏结局！"）

4. **数据填充**
   - 每个剧本至少1个Secret End
   - 设定触发条件（如：3条路线都达到Good End + 总好感度≥240）

### 工作量评估

| 任务 | 工时 |
|------|------|
| 数据库字段新增 | 2h |
| 后端结局判断逻辑 | 8h |
| 前端展示效果 | 8h |
| Secret End内容设计（3个剧本） | 6h |

## CR-033: 节点类型完善

### 问题描述

文档要求6种节点类型，当前实现不完整：

| 节点类型 | 文档要求 | 当前实现 | 状态 |
|----------|----------|----------|------|
| 开场节点 | 📌 人工预设 | 无此类型 | ❌ 缺失 |
| AI对话段落 | 🤖 AI填充 | 无此类型 | ❌ 缺失 |
| 选择点 | 🔀 分支选择 | choice(1个) | ⚠️ 不足 |
| 收敛节点 | 📌 强制汇合 | converge_node(1个) | ⚠️ 不足 |
| 结局节点 | 📌 人工预设 | ending(27个) | ✅ 充足 |
| CG解锁点 | 📌 人工预设 | cg_trigger(4个) | ⚠️ 不足 |

### 优化方案

1. **新增节点类型**
   ```sql
   -- node_type枚举值
   -- opening: 开场节点（第一章起始）
   -- dialogue: AI对话段落
   -- choice: 选择点（已有）
   -- converge_node: 收敛节点（已有）
   -- ending: 结局节点（已有）
   -- cg_trigger: CG解锁点（已有）
   ```

2. **数据填充**
   ```
   开场节点：每个剧本1个（共3个）
   AI对话段落：每章至少5个（共60个）
   选择点：每章至少2个（共24个，当前仅1个）
   CG解锁点：每章至少1个（共12个，当前仅4个）
   ```

3. **AI对话段落实现**
   - 预设对话模板（人工）
   - AI动态生成（根据好感度/剧情状态）
   - 混合模式（模板+AI补充）

## CR-035: 时间约束规则

### 问题描述

文档要求"3分钟内进入第一个选择点"，当前系统无此约束。

### 优化方案

1. **后端改动**
   ```python
   # 游戏开始时记录时间
   game_session.started_at = datetime.now()
   
   # 每次获取节点时检查
   if node.node_type == 'choice':
       time_elapsed = (datetime.now() - game_session.started_at).seconds
       if time_elapsed > 180:  # 3分钟
           # 记录超时事件
           log_timeout_event(game_session.id)
   ```

2. **前端改动**
   - 显示倒计时（可选）
   - 超时提示（"剧情节奏较慢，建议加快选择"）

3. **规则引擎**
   - 超时不影响游戏，但记录数据用于分析

| 任务 | 工时 |
|------|------|
| 后端时间记录 | 4h |
| 超时检测逻辑 | 4h |

## CR-036: 好感度触发CG规则

### 问题描述

文档要求"好感度累计到暧昧(20+)时触发第一张CG"，当前系统未绑定此规则。

### 优化方案

1. **后端改动**
   ```python
   # 好感度变化时检查
   if affection_delta > 0:
       new_affection = current_affection + affection_delta
       if new_affection >= 20 and current_affection < 20:
           # 触发CG解锁
           unlock_cg(user_id, character_id, cg_id='first_cg')
   ```

2. **CG解锁规则**
   ```
   好感度20+：解锁第一张CG（暧昧）
   好感度40+：解锁第二张CG（信赖）
   好感度60+：解锁第三张CG（亲密）
   好感度80+：解锁第四张CG（挚爱）
   ```

3. **前端改动**
   - CG解锁时显示提示"解锁新CG！"
   - 相册中显示解锁进度

### 工作量评估

| 任务 | 工时 |

## CR-037: 选择项数量统一

### 问题描述

文档要求每个选择点2-4个选项，CR-029要求统一改为3个。当前系统数据不一致。

### 当前数据

```
选择项数量分布：
- 1个选项：6个节点
- 2个选项：27个节点
- 3个选项：25个节点
- 4个选项：4个节点
```

### 优化方案

1. **数据填充**
   - 2个选项的节点：补充第3个选项
   - 1个选项的节点：补充为3个选项
   - 4个选项的节点：保持不变（符合2-4范围）

2. **补充选项类型**
   - 积极选项（+好感度）
   - 消极选项（-好感度）
   - 中性选项（0好感度）

3. **数据迁移脚本**
   ```sql
   -- 为2选项节点补充第3个选项
   INSERT INTO node_choices (node_id, text, affection_delta, ...)
   SELECT node_id, '（保持沉默）', 0, ...
   FROM node_choices
   GROUP BY node_id
   HAVING COUNT(*) = 2;
   ```

### 工作量评估

| 任务 | 工时 |
|------|------|
| 数据分析 | 2h |
| 补充选项设计 | 4h |
| SQL脚本编写 | 2h |
| 数据填充执行 | 1h |
| 测试验证 | 1h |
| **合计** | **10h（1.5天）** |
